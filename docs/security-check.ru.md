# Проверка исправлений безопасности: разбор кода

Документ объясняет добавленный код и по ходу дела — конструкции Go, которые в нём
встречаются. Рассчитан на читателя, который Go не знает.

В самом коде комментарии объясняют только принятые решения: почему сделано так, а не
иначе. Объяснения самого языка вынесены сюда, чтобы не раздувать исходники.

## Задача

Nextcloud умеет сказать «есть более новая версия», но не говорит, чинит ли она
уязвимости. Метрика `nextcloud_system_update_available` из-за этого поднимала алерт на
каждый рядовой патч-релиз. Теперь она равна единице только если обновление действительно
закрывает уязвимость.

Отдельной опции включения нет: проверка работает всегда вместе с `--enable-info-update`.
У метрики появилась метка `advisories_available`, показывающая состояние источника
данных: пока она равна `false`, проверка выполнена не была и метрика сообщает о любом
обновлении, как раньше. Номера уязвимостей, которые закрывает обновление, в метки не
попадают — они целиком пишутся в лог.

Разделение на три файла не косметическое: у каждого своя зона ответственности, и
`security.go` ничего не знает ни про HTTP, ни про формат ответа GitHub.

## Минимум про Go, чтобы читать дальше

Если вы уже знаете Go, пропустите этот раздел.

**Функция и возврат нескольких значений.** В Go функция может вернуть несколько значений
сразу. Это основной способ сообщать об ошибке или о неудаче:

```go
func parseVersion(raw string) (version, bool)
```

Возвращает разобранную версию и признак успеха. Вызов выглядит так:

```go
parsed, ok := parseVersion("34.0.1")   // := объявляет новые переменные
if !ok { ... }                         // ! это "не"
```

**Ошибка — обычное значение.** Тип `error` — это значение, которое либо `nil` (ошибки
нет), либо содержит описание проблемы. Проверка ошибки после каждого вызова — норма:

```go
if err := c.refresh(ctx); err != nil {
    // что-то пошло не так
}
```

Запись `if x := ...; условие` объявляет переменную, видимую только внутри `if`.

**Тип и методы на нём.** Свой тип можно объявить поверх существующего и навесить на него
функции — методы:

```go
type version []int                       // версия это срез (список) чисел

func (v version) major() int { ... }     // метод: v это "получатель"
```

Вызывается как `v.major()`. Получатель бывает значением (`v version`) или указателем
(`c *SecurityChecker`). Указатель нужен, когда метод меняет объект или когда объект
большой и копировать его не хочется.

**Указатель может быть nil, и метод на нём всё равно вызовется.** Это особенность Go,
которая здесь используется намеренно: методы `SecurityChecker` проверяют `c == nil` сами
и отвечают «не знаю». Поэтому вызывающему коду не нужно писать проверку на каждый вызов.

**Структура.** Набор именованных полей. Поля с маленькой буквы видны только внутри
пакета, с большой — снаружи. Отсюда `SecurityChecker` (публичный, его создаёт `main.go`)
и `advisoryFetcher` (внутренний).

**Теги полей.** Строка в обратных кавычках после поля управляет разбором JSON:

```go
GHSAID string `json:"ghsa_id"`
```

Поля ответа, которых нет в структуре, просто отбрасываются — перечислять всё не нужно.

**Указатель как «значения не было».** Обычная строка не отличает «поле отсутствовало» от
«поле было пустым». Указатель отличает: `nil` значит, что поля не было.

```go
WithdrawnAt *string `json:"withdrawn_at"`
```

**Горутина.** `go f()` запускает функцию параллельно и немедленно возвращает управление.
Так работает фоновое обновление: скрейп Prometheus никогда не ждёт GitHub.

**Мьютекс.** Раз есть параллельность, к общим данным нельзя обращаться одновременно.
`sync.RWMutex` разрешает много одновременных читателей, но только одного писателя. Здесь
читателей много (каждый скрейп), а писатель один и появляется раз в 12 часов.

**Контекст.** `context.Context` — способ сказать «прекращай». Передаётся первым аргументом
и позволяет отменить http-запрос и завершить фоновую горутину.

**defer.** `defer res.Body.Close()` выполнится при выходе из функции по любой причине.
Тело http-ответа обязательно закрывать, иначе соединение не вернётся в пул и утечёт.

**select.** Ждёт того из нескольких событий, которое произойдёт раньше. В цикле обновления
это «истёк таймер» или «контекст отменён» — без него отмена не сработала бы до конца
двенадцатичасовой паузы.

## `internal/metrics/version.go`

Самый маленький файл, но без него всё остальное не имеет смысла.

Версии приходят с разным числом компонентов: Nextcloud сообщает свою версию четырьмя
числами (`34.0.2.1`), а advisories указывают исправленные версии тремя (`34.0.1`).
Сравнивать их как строки нельзя: `34.0.10` меньше `34.0.9` в лексикографическом порядке,
хотя по смыслу больше.

Поэтому версия разбирается в список чисел и сравнивается покомпонентно. Отсутствующие
компоненты считаются нулём, поэтому `34.0.1` и `34.0.1.0` равны, а `34.0.2.1` больше
`34.0.2`. Это и позволяет сравнивать четырёхкомпонентную версию Nextcloud с
трёхкомпонентной из advisories.

`major()` возвращает первый компонент — номер ветки. У пустой версии он равен `-1`, чтобы
она не совпала по ветке ни с чем, включая другую пустую.

## `internal/metrics/advisories.go`

### Откуда берутся данные и почему именно оттуда

Единственный источник, отвечающий на вопрос «в какой версии уязвимость исправлена», —
список security advisories репозитория `nextcloud/security-advisories` на GitHub.
Глобальный GitHub Advisory Database и OSV.dev по Nextcloud пусты, а release notes не
упоминают исправления безопасности вовсе, потому что такие правки мержатся из приватных
форков и в changelog не попадают.

Адрес запрашивается с сортировкой по дате публикации по возрастанию. Это не случайность:
пагинация здесь курсорная, и при таком порядке новые записи дописываются в конец, а уже
отданные страницы не сдвигаются. При сортировке по `updated` запись, отредактированная в
середине обхода, может быть пропущена.

### Два правила сопоставления

Главное место файла — метод `fixes`, решающий, будет ли уязвимость закрыта переходом с
текущей версии на доступную.

Запись про уязвимость перечисляет версии, в которых она исправлена, — по одной на каждую
поддерживаемую ветку, например `32.0.12`, `33.0.6` и `34.0.1`.

**Правило первое:** если на нашей ветке исправление уже установлено, запись нас не
касается. Проверять надо самую большую из версий нашей ветки, а не любую: если запись
перечисляет `31.0.1` и `31.0.7`, а установлена `31.0.3`, то по `31.0.1` мы выглядим
исправленными, хотя нужного `31.0.7` у нас нет.

**Правило второе:** иначе уязвимость будет закрыта, если какая-то из исправленных версий
больше текущей и не больше доступной.

Вместе правила дают верный ответ и при переходе между ветками. Пример: установлена
`32.0.14`, доступна `33.0.6`, исправления перечислены как `32.0.12` и `33.0.6`. Второе
правило само по себе сочло бы обновление нужным, потому что `33.0.6` больше `32.0.14`. Но
первое правило видит, что `32.0.12` у нас уже есть, и отбрасывает запись. Без этого
любой, кто в порядке на старой ветке, получал бы ложное срабатывание на каждом скрейпе.

### Отбор нужного продукта

В том же репозитории публикуются advisories по остальным продуктам Nextcloud — Talk,
Desktop, Deck, Tables, — и их номера версий пересекаются с серверными. Поэтому имя пакета
сверяется со списком известных написаний, а не ищется как подстрока: свободный поиск
затащил бы в сравнение чужие версии.

Платная редакция публикуется под ecosystem `nextcloud enterprise` (в части записей — с
опечаткой `nextcloud entreprise`), и её версии состоят из четырёх чисел, которым не
соответствует ни один публичный релиз. Точное сравнение ecosystem с `nextcloud` её
отсекает.

### Самое неприятное место: разбор версий из свободного текста

Поле `patched_versions` заполняется людьми и приходит в разном виде: `32.0.12, 33.0.6`,
`>=32.0.0, >=33.0.0` (без пробела), ` >= 29.0.0, ...` (с пробелом в начале), просто
`31.0.1`.

У части записей поля перепутаны местами: в `patched_versions` лежат неравенства, а сами
версии — в `vulnerable_version_range` (например, CVE-2025-47791). Такие записи
распознаются по тому, что из `patched_versions` не удалось получить ни одной версии, а из
`vulnerable_version_range` получился чистый список чисел. Нормальный
`vulnerable_version_range` почти всегда содержит знак неравенства, поэтому на исправных
записях этот запасной путь не срабатывает.

Разбор терпим к мусору: всё, что не является чистым номером версии, молча отбрасывается.

### Выкачка страниц

Ошибка на любой странице прекращает обход и не возвращает ничего. Это важно: неполный
список выглядел бы как отсутствие уязвимостей и мог бы скрыть обновление безопасности.

Адрес следующей страницы берётся из заголовка `Link`. Сверяются только схема и хост. Путь
сверять нельзя: GitHub отдаёт следующую страницу по другому пути, с числовым
идентификатором репозитория вместо его имени. Проверка хоста нужна, чтобы промежуточный
прокси не смог увести выкачку на посторонний адрес.

Счётчик страниц — предохранитель от бесконечного обхода, если `Link` вдруг зациклится сам
на себя. Сейчас страниц три, так что запас десятикратный.

## `internal/metrics/security.go`

### Числа, определяющие поведение

- **12 часов** между обновлениями. GitHub без токена разрешает 60 запросов в час на
  IP-адрес. Полная выкачка стоит три запроса, поэтому это шесть запросов в сутки — с
  большим запасом.
- **15 минут** до повтора после неудачи.
- **48 часов** — после какого возраста снимок считается непригодным. Список advisories
  только пополняется, поэтому опасность устаревшего снимка в том, что в нём не будет
  свежей записи, и метрика покажет ноль при реально нужном обновлении безопасности. Это
  худшее из возможных поведений, поэтому у снимка есть жёсткий срок годности: четыре
  пропущенных цикла обновления, и он перестаёт использоваться.
- **30 секунд** таймаут одного запроса. Это отдельный таймаут, не связанный с `--timeout`:
  тот задаёт ожидание Nextcloud внутри скрейпа и измеряется секундами, а здесь запрос
  идёт в фоне и торопиться некуда.

### Снимок

Результат одной успешной выкачки — неизменяемый снимок. После публикации он никогда не
меняется: следующая выкачка создаёт новый и заменяет указатель. Благодаря этому читателям
достаточно скопировать указатель под блокировкой, а дальше работать без неё.

Если в ответе не оказалось ни одной пригодной записи про Nextcloud Server, это считается
ошибкой, а не «уязвимостей нет». Так выглядит, например, переименование ecosystem на
стороне GitHub. Старый снимок при этом сохраняется, а если его нет, проверка остаётся
отключённой и метрика ведёт себя как раньше. Считать, что уязвимостей нет, здесь нельзя —
это молча спрятало бы обновления безопасности.

### Ответ на вопрос

`Check` возвращает два значения: список номеров уязвимостей и признак того, что ответ
вообще получен. Если признак равен `false`, ответа нет (проверка выключена, данных нет,
версии не разобрались), и вызывающий обязан сообщить об обновлении, как делал до
появления проверки.

Список сортируется по убыванию, то есть свежие уязвимости идут первыми: номера CVE
начинаются с года.

У части записей номер CVE ещё не присвоен — тогда используется идентификатор GHSA.

### Почему вывод не повторяется на каждом скрейпе

`Check` вызывается на каждый скрейп Prometheus, то есть раз в 15–60 секунд. Без защиты
одна и та же строка повторялась бы в логе бесконечно. Поэтому последнее сообщение
запоминается, и повтор не выводится. Строка меняется, когда меняется версия Nextcloud,
доступное обновление или сам список уязвимостей — то есть ровно тогда, когда о ней есть
смысл сообщить.

Отдельно: после каждой успешной выкачки память сбрасывается. Данные новые, значит разбор
надо показать заново, даже если словесно результат совпал с предыдущим. Иначе список CVE
попал бы в stdout один раз за всю жизнь процесса.

## `internal/metrics/collector.go`

Здесь принимается решение о значении метрики:

- обновления нет — ноль, как и раньше;
- обновление есть, но проверка ответила «известных исправлений безопасности нет» — ноль;
- во всех остальных случаях, включая «ответа нет», — единица.

### Почему номера уязвимостей не стали меткой

Список неограничен: одно обновление может закрывать десятки уязвимостей. Метка с таким
значением породила бы огромную строку в каждой серии, а при каждом изменении списка —
новую серию в Prometheus. Поэтому список уходит в лог, а в метрику попадает только
булево состояние источника.

### Что означает добавление метки

`advisories_available` описывает состояние источника advisories, а не решение по этой
конкретной паре версий. Поэтому метка осмысленна и когда обновления нет вовсе: по ней
видно, работает ли проверка в принципе.

Добавление метки меняет идентичность серии: старые серии `nextcloud_system_update_available`
без этой метки исчезнут, появятся новые. Запросы вида
`nextcloud_system_update_available > 0` продолжат работать, запросы с точным перечислением
меток — нет.

## `main.go`

Проверка создаётся и запускается только если включена метрика обновления. В противном
случае в коллектор передаётся `nil`, и все вызовы к нему безопасно отвечают «не знаю».

Фоновое обновление запускается до регистрации коллектора, чтобы первая выкачка началась
как можно раньше.

## Как это выглядит в работе

```plain
Security check: loaded 127 advisories for Nextcloud Server.
Security check: update 32.0.5.2 -> 32.0.14.1 contains fixes for 8 vulnerabilities: CVE-2026-61527, CVE-2026-45691, CVE-2026-45690, CVE-2026-45285, CVE-2026-45282, CVE-2026-45281, CVE-2026-45157, CVE-2026-45155.
```

И на обновлении без исправлений безопасности:

```plain
Security check: update 34.0.2.1 -> 34.0.3.2 contains no known security fixes.
```

Метрика:

```plain
nextcloud_system_update_available{version="34.0.0.1",available_version="34.0.3.2",advisories_available="true"} 1
```

## Что стоит знать про ограничения

- **Нужен исходящий доступ к `api.github.com`.** Токен не нужен.
- **Кэш живёт в памяти.** Перезапуск экспортёра стоит одной выкачки; на диск ничего не
  сохраняется, чтобы не заводить ещё одну настройку.
- **Проверка ошибается в сторону «сообщить».** Advisories указывают версии, содержащие
  исправление, но диапазоны затронутых версий в тех же записях ненадёжны и не
  учитываются. Поэтому обновление может быть признано важным даже если установленная
  версия никогда не была уязвима.
- **Сигнала «есть любое обновление» больше нет.** Метка `available_version` по-прежнему
  заполняется тем, что сообщил Nextcloud, поэтому
  `nextcloud_system_update_available{available_version!=""}` близко к прежнему сигналу, но
  не точно: Nextcloud выставляет флаг обновления и когда предложенная версия совпадает с
  установленной, и метка тогда непуста при отсутствии обновления.

## Сборка в GitHub Actions

Заодно переделана сборка. Было три файла, два из которых почти совпадали; стало три с
разными ролями:

| Файл | Роль |
|---|---|
| `ci.yml` | push в main и pull request: линтеры, тесты, образ |
| `release.yml` | теги `v*`: тесты и публикация образа |
| `image.yml` | общая сборка образа, вызывается из двух предыдущих |

Что изменилось по существу:

- **Убран `docker/setup-qemu-action`.** Он не использовался никогда: сборочный слой
  Dockerfile закреплён за `$BUILDPLATFORM` и кросс-компилирует через `GOOS`/`GOARCH`, а
  финальный слой только копирует в себя файлы и ничего не выполняет. Проверено:
  `docker buildx build --platform linux/arm64` собирается на amd64 без QEMU за секунды и
  даёт настоящий бинарь ARM aarch64.
- **На pull request собирается только амд64.** Образ там всё равно выбрасывается.
- **Добавлен кэш слоёв buildx** (`type=gha`). Без него каждая сборка заново выкачивает
  модули и компилирует всё с нуля.
- **Добавлен `concurrency`**: новый пуш в pull request отменяет предыдущий прогон.
- **Версия Go больше не прибита в трёх местах** — берётся из `go.mod`.
- **Права выдаются по джобам**, а не всему workflow: запись в packages нужна только
  сборке образа.
- **Инструменты bingo кэшируются** — иначе promtool компилируется из исходников на каждый
  прогон линтера.

## Проверка

```bash
make test          # тесты
make lint          # golangci-lint + promtool
go test -race ./...
```
